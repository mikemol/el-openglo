# Cotype — EL-Indiglo KDE theme

## Goal (as stated)
KDE theme that looks like the electroluminescent displays of childhood digital watches
(Timex Indiglo era: ZnS:Cu phosphor, blue-green ~505 nm glow, dark LCD, ghost segments).

## Shadows (registered, axis-tagged)

- [100] **Scope decomposition.** "KDE theme" decomposes into: (a) system color scheme
  (.colors — largest visible surface, applies to all Qt/KDE apps), (b) Konsole scheme,
  (c) wallpaper (signature element), (d) README/install. Deferred: Aurorae decoration,
  full Plasma desktop theme (SVG set), Kvantum, GTK sync — registered as gaps, not built.
- [100] **Palette invariant (the either/or bottoming out).** Two candidate looks:
  backlight-OFF (dark panel, glowing marks) vs backlight-ON (glowing panel, dark digits).
  Common structure: both are the *same* two-material system — phosphor glow vs unlit LCD —
  differing only in which is figure and which is ground. Resolution: OFF is the ambient
  state (usable as a desktop), ON is reserved for **selection** — selecting text/items
  "presses the Indiglo button" (glow background #00CDB0, dark foreground #04211D).
  Neither branch discarded; ON survives as the selection state, not residue.
- [110] **Token system** (mediated goal→shadows→artefact):
  - panel-off  #060B0D  (view bg, deepest)
  - case       #0C1517  (window bg) / button #122225
  - body-glow  #8CE8DA  (normal fg — glow at reading intensity)
  - hot-glow   #A8FFF2  (active fg)
  - el-core    #00E0C2  (focus decoration) / selection bg #00CDB0
  - ghost      #3D6660  (inactive fg — unlit segment)
  - amber-EL   #FFB454  (neutral; amber EL panels are period-authentic, aircraft/pagers)
  - coral      #FF6E63  (negative), spring #55F0A0 (positive), cyan link #45D8F0
- [010] **Wallpaper artefact.** Seven-segment field: ghost "88:88 88" under lit "12:00"
  flashing-clock motif (the just-reset watch), glow via gaussian filters, faint panel
  vignette. Generated by script (kept in package) so it can be re-parameterized.

# Installing EL Indiglo on Kubuntu (⊕VER)

## One-time install (system-wide, apt-managed)

    sudo apt install ./el-indiglo-themes_1.0.0_all.deb

This installs — for all six phosphor variants — the color schemes, Konsole
schemes, Aurorae window decorations, Plasma styles, the segment/dot-matrix
clock plasmoid, and the segment/matrix fonts (font cache refreshed
automatically). It also installs the `el-indiglo-apply` helper.

Clean uninstall any time:

    sudo apt remove el-indiglo-themes

## Apply a variant (per-user, no root)

    el-indiglo-apply EL-Indiglo

Variants: `EL-Indiglo` `EL-Indiglo-Lit` `EL-Azure` `EL-Azure-Lit`
`EL-Amber` `EL-Amber-Lit`. The helper selects the color scheme and Plasma
style live, writes your per-user GTK (`~/.config/gtk-{3,4}.0/gtk.css`) and
Kvantum config, and sets the Aurorae decoration. Re-run it any time to switch
variants — it's idempotent.

## Finishing touches (manual, once)

- **Qt widget style → Kvantum**: System Settings → Colors & Themes →
  Application Style → set to *kvantum* (so the Kvantum config the helper wrote
  takes effect). GTK3 apps also want the *adw-gtk3* theme active.
- **Panel clock**: right-click the panel → Add Widgets → search "EL Segment
  Clock" → drag to the panel. Configure for display type (7/9/14/16/22-segment
  or 5×7/5×8 dot-matrix), content template, scroll, and ghost segments.
- **Wallpaper**: right-click desktop → Configure → Wallpaper → Image → the
  EL-Indiglo wallpapers are under the system wallpapers list.

## Why a .deb plus a helper (not one or the other)

The install is a mapping from built files to destinations. Most land in system
paths (`/usr/share`) and are exactly what apt manages well. But GTK's `gtk.css`
and Kvantum's config are read per-user from `~/.config` — a .deb must never
write to a user's home, so those are applied by the helper you run once. Same
mapping, two scopes, honestly split.

## Session 56 — STANDARDS INVENTORY (reground: what do we actually measure against?)
- [drift: clean, v1.19.1]. Read the gate source (not recalled). Honest split:
  EXTERNAL STANDARDS vs OUR CONSTRUCTIONS vs APPROXIMATIONS.

### A. Real external standards / specs (verifiable, third-party):
1. sRGB (IEC 61966-2-1) — the device colorspace; its EOTF (12.92 / 0.03928 knee,
   ((c+0.055)/1.055)^2.4 gamma) is implemented in _wcag_L for linearization.
2. WCAG 2.x contrast ratio — (L1+0.05)/(L2+0.05) on sRGB relative luminance
   (0.2126R+0.7152G+0.0722B linear). = wcag_ratio. Used for ALL lit/ghost/void
   contrast gates. This is the W3C accessibility standard.
3. CIECAM02-UCS (Luo/Cui/Li 2006) — the uniform colour-appearance space we take
   distances IN (via colorspacious cspace_convert to CAM02-UCS). Perceptual dE =
   Euclidean L2 norm in CAM02-UCS. (Not CIE76/94/2000 Lab — a NEWER, more uniform
   space. Honest: our "dE" is CAM02-UCS distance, not a CIELAB deltaE.)
4. CVD (colour-vision-deficiency) simulation — TWO models on purpose:
   · Machado, Oliveira & Fernandes (2009), severity 100, via colorspacious
     sRGB1+CVD, for protan/deutan/tritan.
   · Brettel, Viénot & Mollon (1997), via daltonlens Simulator_Brettel1997, second
     tritan model. Two models so distinctness survives MODEL uncertainty, not one
     sim.
5. Okabe & Ito (2008) "Color Universal Design" palette — the empirical
   colour-blind-safe constellation. We don't hand-pick a distinctness floor; we
   DERIVE it as the tightest worst-view pair INSIDE Okabe-Ito (reference_floors),
   so "distinct enough" means "at least as separated as the reference shape's own
   closest admissible pair." Standard-anchored, not arbitrary.
6. Colorspaces in play: sRGB (device I/O), linear-light RGB (WCAG luminance),
   LMS cone space (inside Brettel/Machado CVD sims), CIECAM02-UCS (perceptual
   distance). CIE XYZ implicitly (transform pivot inside colorspacious).

### B. Our own constructions (NOT standards — engineering invariants we defined):
- feasible_floor(lit,bg)=min(3.0, sqrt(lit/bg span)*0.95): acknowledges both-3:1
  is geometrically impossible on narrow-span lit variants; not a spec.
- derive_ghost max-min balance; stretch_lit; STRETCH_TARGET 3.0, chroma floor 40.
- OLED_VOID_MAX_LUM = 0.02 (2% rel-lum): OUR "reads as true black on OLED"
  threshold. Defensible (~2-4 nits of SDR white) but not a named standard.
- ⊕GLANCE-AUDIT: parsing-mode floors (looked_at 3.0 anchored to WCAG large-text;
  glanced_at 5.5 = OUR choice, ~2x, first-pass); bloom 1.30 / stroke 1.15 bonuses
  = OUR heuristic perceptual weightings (labeled residue ⊕GLANCE-CALIBRATE).
- Perceived brightness = luminance x AREA (stroke-weight): real optics, but our
  1.54x figure is a design choice not a threshold.

### C. Honest gaps / where we are NOT standards-rigorous:
- No formal WCAG 2.2 SC conformance CLAIM (we USE the contrast math; we don't
  assert AA/AAA conformance for the whole UI — a theme can't, since app content
  varies). We measure the SEGMENT/GHOST/VOID relationships, not full-UI SC.
- APCA (WCAG 3 draft contrast, the WCAG-2-successor) NOT used — we use WCAG 2
  ratio. Residue ⊕APCA-CROSSCHECK: WCAG2 is known to mis-rank some dark-mode
  pairs; APCA (Lc) could cross-check the dark-ground legibility. Worth it since the
  whole theme is dark-on-void.

- dE is CAM02-UCS L2, not CIEDE2000 — a defensible modern choice, but not the most
  commonly-cited deltaE; note when communicating.
- glanced_at floor + bonuses uncalibrated (⊕GLANCE-CALIBRATE).
